# Project Summary — yet_another_tracker

> Видение, принципы, скоуп. Источник истины для всех LLM, работающих с проектом.

## Видение

Персональное PWA-приложение для контроля cashflow. Решает: мгновенный ввод трат, осмысленную аналитику с action points, контроль регулярных платежей через Telegram. В v2+ — AI-слой для проактивных подсказок и диалогов с собственным датасетом.

Главный пользовательский сценарий: «потратил → ввёл за 5 секунд → забыл». Всё остальное — производное от качественно набранного датасета.

## Целевая аудитория

**Первичная (v1):** автор-PM, нужен полный контроль над финансами, Pro-режим с детальной кастомизацией.

**Вторичная (v2+):** люди с разным финансовым стилем и уровнем технической продвинутости. Поддерживаются через два режима UI: Common (простой) и Pro (полная кастомизация).

## Принципы

1. **Делается для себя по продуктовым принципам.** Архитектура готова к масштабированию (multi-user в БД, чистый сервисный слой, Common/Pro как сквозной принцип). Контент и приоритизация — под автора.
2. **Скорость ввода — священна.** Калькулятор-первый экран, минимум кликов, оптимистичный UI, local-first запись.
3. **Native feel.** PWA с ощущением нативного мобильного приложения.
4. **AI-ready через границы, не через инфраструктуру.** В v1 AI не реализуется, но архитектура подготовлена: сервисный слой, нормализованные форматы, журнал событий пользователя.
5. **Данные принадлежат пользователю.** JSON-экспорт, читаемый самим приложением. Гарантия выхода из продукта.
6. **Авторитет — у пользователя, не у AI.** AI генерирует предложения, БД меняется только через подтверждение.
7. **Безусловное доверие модулю ввода данных.** Это критический функционал, который не должен терять или искажать данные ни при каких обстоятельствах. Все остальные модули могут ломаться, ввод — нет.
8. **Чёткая граница v1/v2/v3.** В v1 — фундамент и базовый функционал. AI, расширенная аналитика, масштабирование — позже.

## Стек

- **Frontend:** Next.js 15 (App Router) + TypeScript + Tailwind + shadcn/ui
- **Charts:** Apache ECharts через `echarts-for-react`
- **Backend:** Next.js Route Handlers + Prisma + PostgreSQL
- **Auth:** NextAuth.js, Google OAuth в v1; Яндекс ID и Telegram-login в v2
- **Backup:** Backblaze B2 (серверный дамп) + JSON-экспорт для пользователя в Google Drive
- **Cache/Queue:** В v1 — НЕТ Redis/BullMQ. Используется Postgres-воркер по cron для регулярных задач. Redis+BullMQ возвращаются в v2+ при появлении AI-задач.
- **Notifications:** свой Telegram-бот на Node.js, в v1 только исходящие
- **Analytics product:** typed `track()` заглушки в v1; PostHog Cloud free tier при необходимости (НЕ self-hosted на этом VPS)
- **Infra:** Docker Compose + Caddy + GitHub Actions, всё на VPS в Нидерландах (2 vCPU / 4 GB RAM)
- **UI workflow:** Claude Design → handoff bundle → Codex. Source of truth — `DESIGN.md` + GitHub-интеграция Claude Design к репо.

## Концептуальная модель данных

### Сущности

**1. Пользователь (`user`).** Профиль, выбранный тон AI (для v2), режим UI (Common/Pro), роль (`user` / `admin`).

**2. Счёт (`account`).** Источник денег. Три группы:
- **Current** — карты, наличные, расчётные счета. Положительный баланс. Оперативные средства.
- **Savings** — депозиты, цели накопления, сбережения. Положительный баланс. Изолированы от ежедневных трат.
- **Debt** — кредитки, кредиты наличными, займы. **Единственная группа с особой семантикой движений (см. ниже)**.

**3. Категория (`category`).** Иерархическое дерево. В v1 — глубина до 2 уровней (Common). Произвольная глубина — Pro-разметка. Дефолтные категории + пользовательские. Атрибут «постоянное/переменное» (дефолт на категории, override на транзакции).

**4. Транзакция (`transaction`).** Базовая единица движения денег.
- `amount` (Decimal) + `currency` (в v1 только RUB)
- Дата/время
- Счёт (откуда/куда)
- Категория-лист (для расходов/доходов)
- Тип: `expense` / `income` / `transfer`
- Статус: `confirmed` / `pending` / `rejected` / `cancelled`
- Опционально: `gross_amount` + `net_amount` (для компенсаций бонусами), `linked_transaction_id` (для частичных возвратов), `client_generated_id` (для идемпотентности при local-first вводе), `tier_marker`

**5. Правило (`rule`).** Шаблон регулярных событий: подписка, зарплата, аренда. Любая периодичность. Генерирует pending-транзакции в соответствующие даты.

**6. Период (`period`).** Именованный диапазон времени с типом (отпуск, командировка, ремонт). Используется в фильтрах аналитики для исключения.

**7. Цель накопления (`savings_goal`).** Произвольное название, тип (целевая / просто отложено / liability-as-savings), опциональная целевая сумма и дата, ежемесячный взнос. Связана со счётом группы `savings`.

### Семантика движений

- **Расход (expense):** деньги уходят со счёта `current` или приходят на счёт `debt` (момент покупки с кредитки).
- **Доход (income):** деньги приходят на счёт `current`.
- **Transfer:** деньги переходят между счетами без учёта в графиках доходов/расходов.

### Группа Debt — особая

- Покупка с кредитки = расход в момент покупки (счёт `debt`).
- Погашение долга = расход в категории «Обслуживание долга» (механика требует отдельной UX-проработки).
- Категория «Обслуживание долга» исключается из общих графиков расходов по умолчанию.
- 0%-кредитка как savings: пополнение depositа через transfer из debt в savings — работает естественно.

⚠️ **Открытый вопрос:** механика учёта кредитов в аналитике (см. `OPEN_QUESTIONS.md`).

## Функциональный скоуп v1

### Что входит

- Аутентификация через Google.
- Калькулятор-экран как единая точка входа для расходов, доходов и transfers.
- Иерархия категорий, до 2 уровней в Common, произвольная в Pro-разметке.
- Несколько счетов (current, savings, debt).
- Транзакции со статусами, компенсации, флаги постоянное/переменное.
- Правила регулярных платежей с генерацией pending.
- Запланированные разовые платежи (через тот же статус `pending`).
- Telegram-бот с 3 типами уведомлений: pending к подтверждению, плановые напоминания, операционные алерты для admin.
- Периоды с типами и возможностью исключения из аналитики.
- 3-4 готовых дашборда + exploration через таблицу с фильтрами.
- Цели накопления + расчёт рекомендуемого дневного бюджета на главном экране.
- Раздел подписок и базовый прогноз cashflow.
- Tier-разметка Common/Pro на всех фичах (без UI-разделения в v1).
- JSON-экспорт/импорт с `schemaVersion`.
- PWA с оффлайн-вводом (IndexedDB), ручная кнопка синхронизации.
- Архитектурные хуки под AI (сервисный слой, формат агрегатов, журнал событий).
- Schema constraints, read-after-write валидация, daily reconciliation report для критичности модуля ввода.

### Что НЕ входит в v1

- Мультивалютность (только RUB).
- Любая AI-функциональность.
- Inline-кнопки в Telegram и интерактивные сценарии.
- Когортный анализ, pivot tables, произвольные многомерные срезы.
- Multi-user UI, семейный доступ.
- Импорт из банков, OCR чеков.
- Криптовалюты, инвестиции, портфели.
- Геолокация.
- Полноценный Common-режим UI (только разметка).
- Нативное iOS-приложение.

## Что планируется в v2

- AI-чат с цитированием данных, AI-отчёты по запросу, AI-помощь при вводе.
- Inline-кнопки в Telegram, pending-сценарии с обратной связью.
- Автоконвертация валют по курсам ЦБ РФ.
- Яндекс ID и Telegram-login.
- Расширенная аналитика.
- Self-hosted PostHog (опционально, при расширении VPS).

## Что планируется в v3+

- Полноценный Common-режим UI и переключатель.
- Multi-user семейный режим.
- OCR чеков через QR-коды ФНС.
- Симуляция «что если» сценариев в AI.
- Mobile native app (если PWA-ограничения окажутся блокером).

## Подход к разработке

- **Living roadmap** в виде `PLAN.md`, обновляемого при каждом значимом решении.
- **Тактический бэклог** — GitHub Issues с labels, Milestones.
- **Декомпозиция:** эпики → стори → задачи. Груминг на уровне стори, перед каждой стори — отдельный заход с LLM.
- **Git flow:** `feature/*` → `develop` (staging) → `main` (prod). Деплой через GitHub Actions.
- **Stage как daily driver, prod как backup-копия с задержкой 24ч.** Перед каждым деплоем на stage — автотесты модуля ввода. Если тесты упали — деплой блокируется.
- **Schema constraints + read-after-write + daily reconciliation** как защитный пояс модуля ввода.
- **PR-инстансы** для UI-изменений с синтетическими данными.
- **Локальная разработка** как safety net для рискованных структурных изменений.
- **Инструменты:** Cursor (14 дней trial) + Codex (основной) + Claude Design (для UI). Claude Code — резерв.

## Принципы AI-архитектуры (для v2+)

- AI читает данные только через сервисный слой.
- AI не пишет в БД. Только предложения через подтверждение пользователя.
- Каждый AI-ответ цитирует конкретные данные.
- Каждый ответ имеет confidence-уровень.
- Тон AI настраивается через выбор из 2-4 примеров в онбординге.
- 3 режима работы AI: реактивный диалог, проактивный наблюдатель, регулярный отчётник.
- Внутренний inbox + Telegram как два канала уведомлений с разной приоритетностью.

## Известные ограничения и риски

1. **PWA на iOS:** push-уведомления хрупкие, IndexedDB может очищаться через ~7 дней неактивности. Компенсация — Telegram-бот + ручная синхронизация.
2. **Лимиты Claude Design:** требует Max-подписку при активной работе с UI, потом откат на Pro.
3. **VPS-ресурсы:** при добавлении PostHog self-hosted или большого числа PR-инстансов потребуется расширение.
4. **Solo разработка с AI-агентами:** требует строгой дисциплины с тестами, миграциями, ревью.
5. **Stage как daily driver:** требует надёжных автотестов модуля ввода и backup-restore цикла.
