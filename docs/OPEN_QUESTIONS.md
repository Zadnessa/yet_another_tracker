# Open Questions

Список открытых вопросов и тем для будущей проработки. Накоплен в ходе обсуждения концепции. Каждый вопрос — кандидат на отдельную задачу «на подумать» в соответствующем эпике или стори.

## Модель данных

### O1. Механика учёта кредитов в аналитике
**Контекст:** Покупка с кредитки = расход в момент покупки. Погашение долга = расход в категории «Обслуживание долга». Возникает дубль в графиках, если суммировать.
**Текущее предложение:** Категория «Обслуживание долга» исключается из общих графиков по умолчанию. Pro-режим может включить.
**Что требует проработки:** UX отображения долговой нагрузки, корректная аналитика для пользователей, активно использующих кредитки.

### O2. UX для разбиения чека на несколько транзакций
**Контекст:** Один тап = одна категория, без splits. Но как объяснить юзеру, что чек из Пятёрочки на 4500₽ надо разбить на «продукты», «бытовая химия», «игрушки»?
**Что требует проработки:** UX-паттерн для не-pro юзеров. Возможно, подсказки или onboarding-туториал на первом сложном чеке.

### O3. Возвраты с частичной отменой и сдвигом во времени
**Контекст:** Расход регистрируется в момент забора с ПВЗ (а не списания с карты). Возврат может быть частичным (вернули не всё). Возврат может прийти на другую карту.
**Что требует проработки:** UX поиска исходной транзакции, sопоставления частичных возвратов, обработки сдвига во времени между фактическим возвратом и регистрацией в приложении.

### O4. UX-вход для пополнения и изъятия средств в накопления
**Контекст:** Принято, что все операции — через калькулятор главного экрана. Но пополнение цели и изъятие из неё — концептуально другая операция (трансфер между группами счетов).
**Что требует проработки:** интуитивный UX выбора «направления операции», визуальное разделение групп счетов в селекторе, отображение целей и их прогресса.

## Telegram-бот

### O5. Список admin-уведомлений
**Контекст:** Третий тип уведомлений — операционные алерты только для admin (`role = admin`).
**Что требует проработки:** конкретный список событий, которые admin должен получать. Сейчас известны: restore drill упал, сервер недоступен, бэкап не загрузился. Что ещё?

## Инфраструктура

### O6. Структура AGENTS.md — best practices research
**Контекст:** Текущая структура AGENTS.md в репозитории — стартовая заглушка.
**Что требует проработки:** research 5-10 примеров AGENTS.md из реальных open-source проектов с активной AI-разработкой. Сопоставление с лучшими практиками. Финальная структура в `docs/agents-md-structure.md` + AGENTS.md.

### O7. Локальное окружение для рискованных изменений
**Контекст:** Stage как daily driver, локальная разработка — safety net.
**Что требует проработки:** настройка локального Docker Compose с синтетическими данными, документация для запуска, чёткое определение «рискованных изменений», требующих локальной проверки.

### O8. Backup и restore drill автоматизация
**Контекст:** Backup сам по себе ничего не гарантирует — нужны регулярные проверки восстановления.
**Что требует проработки:** автоматический скрипт раз в неделю: скачать последний бэкап, развернуть на пустую БД, проверить структуру, удалить. Алерт в Telegram при провале.

### O9. Хранение бэкапов: ротация и retention
**Контекст:** Бэкапы делаются ежедневно. Хранить все — много места.
**Что требует проработки:** ротация — 7 дневных + 4 недельных + 12 месячных, всё остальное удаляется. Где хранятся (Backblaze для серверного, Google Drive для пользовательского JSON).

## UX

### O10. Common-режим UI: как должен выглядеть
**Контекст:** В v1 разметка Common/Pro проставляется, но используется только Pro. Полноценный Common — отдельный эпик в v2+.
**Что требует проработки:** не «прятать кнопки», а **переосмыслить информационную иерархию** для не-pro юзеров. Это полноценная дизайнерская работа.

### O11. Тон AI: онбординг через 2-4 примера
**Контекст:** В v2 при первом запуске AI пользователю показываются 2-4 примера одного и того же сообщения в разных тонах, он выбирает один.
**Что требует проработки:** конкретные формулировки примеров, набор сценариев, для которых нужны примеры (перерасход, цель достигнута, подписка списалась, и т.д.).

### O12. Главный экран — рекомендуемый дневной бюджет
**Контекст:** Формула: (остаток_до_конца_периода − ожидаемые_постоянные_расходы − запланированные_отчисления_на_цели) / оставшиеся_дни.
**Что требует проработки:** конкретный UI индикатора, что показывать рядом (тренд? цель? предупреждение?). Возможно, два числа — «сегодня доступно» и «средний устойчивый» с разной семантикой.

## Аналитика

### O13. Аналитика накоплений: прогресс к целям
**Контекст:** Цели накопления через виртуальные счета.
**Что требует проработки:** какие графики и метрики показывать в разделе целей. Прогресс-бары, прогноз даты достижения, «сколько ещё откладывать».

### O14. Когортный анализ и pivot tables в v2
**Контекст:** Это product-аналитика трат пользователя, не использования приложения.
**Что требует проработки:** конкретные сценарии, которые автор хочет проверить. UX для построения cross-cuts по любым атрибутам.

## AI (v2+)

### O15. Конкретный набор AI-сценариев v2
**Контекст:** Из эмпатии получены 7 персон с 50+ хотелками от AI.
**Что требует проработки:** выбор 5-7 первых AI-сценариев для v2. Приоритизация по ценности vs сложности.

### O16. AI-помощь при вводе («такси до офиса 400»)
**Контекст:** Парсинг свободной строки в структурированную транзакцию.
**Что требует проработки:** где запускается (Telegram? отдельная кнопка в калькуляторе?), как обрабатываются ошибки парсинга, как пользователь корректирует.

### O17. Прогноз cashflow с учётом сценариев «что если»
**Контекст:** Илья из эмпатии хочет «если клиент задержит на 2 недели, что будет?».
**Что требует проработки:** математическая модель прогноза, UX для задания сценариев, как AI это интерпретирует.

## Стратегия

### O18. Когда переключаться на платные подписки
**Контекст:** Cursor 14 дней trial, Claude Max для интенсивной работы с Claude Design.
**Что требует проработки:** конкретный график активации подписок в зависимости от того, какой эпик в работе. Особенно эпики с интенсивной UI-работой.

### O19. Импорт данных из банковских выгрузок
**Контекст:** Прямой импорт из банков — out of scope в v1. Но обычные CSV-выгрузки от банков?
**Что требует проработки:** актуально ли для автора, какие банки, какой формат CSV, как маппить категории.
