# Decisions Log

Лог ключевых архитектурных и продуктовых решений с обоснованием. Если что-то отвергнуто — записано, **почему**, чтобы не возвращаться.

## Архитектура

### A1. Стек: Next.js 15 + Prisma + PostgreSQL
- **Принято:** Next.js 15 как основа.
- **Отвергнуто:** Next.js 14 (устарела), Next.js 16 (рискованно для AI-генерации в мае 2026 — экосистема не догнала).
- **Почему:** Next.js 15 — золотая середина. Стабильна, агенты знают, миграция на 16 будет лёгкой через 6-12 месяцев.

### A2. Один сервис в v1, не микросервисы
- **Принято:** монолит на Next.js, всё в одном репо.
- **Отвергнуто:** разделение на сервис ввода + основное приложение с первого дня.
- **Почему:** для соло-разработчика на старте — overkill. Изоляция input-слоя достигается архитектурно внутри одного сервиса.

### A3. Route Handlers, не API Routes
- **Принято:** только Route Handlers в `app/api/`.
- **Отвергнуто:** смешение с `pages/api/`.
- **Почему:** официальная рекомендация Next.js 15, единый стиль, защита от хаоса при AI-генерации.

### A4. Авторизация в каждом методе, не только в middleware
- **Принято:** двухслойная проверка — middleware + проверка `userId` в каждой Route Handler.
- **Отвергнуто:** доверие только middleware.
- **Почему:** CVE-2025-29927 показала, что middleware может быть обойден.

### A5. БЕЗ Redis/BullMQ в v1
- **Принято:** Postgres-воркер по cron для регулярных задач.
- **Отвергнуто:** Redis + BullMQ с первого дня.
- **Почему:** Redis требует тщательной настройки persistence, BullMQ имеет deprecated паттерны, для v1 нет реальных кейсов под очередь.

### A6. PostHog НЕ self-hosted
- **Принято:** typed `track()` заглушки в v1; PostHog Cloud free tier при необходимости.
- **Отвергнуто:** PostHog self-hosted на VPS.
- **Почему:** требует 4 vCPU / 16 GB RAM, не помещается на текущий VPS.

### A7. Stage как daily driver, prod как backup-копия
- **Принято:** автор живёт на stage. Prod — backup с задержкой 24 часа. Защитный пояс: автотесты модуля ввода блокируют деплой, schema constraints, read-after-write валидация, daily reconciliation.
- **Отвергнуто:** общая stage/prod БД (риск катастрофы). Локальная разработка как основной режим (нет реальных данных). Полная изоляция БД (двойной ввод данных).
- **Почему:** автор должен жить со своими реальными данными в инструменте, который сам разрабатывает.

### A8. AI-ready через границы, не через инфраструктуру
- **Принято:** сервисный слой, нормализованные форматы API, журнал событий пользователя.
- **Отвергнуто:** AI-context таблица, резервированный Python-сервис в Docker Compose, BullMQ под AI-задачи с первого дня.
- **Почему:** делать инфраструктуру под несуществующую функциональность — фальшивая платформа. Все откладывается до первого реального AI-сценария.

### A9. Local-first ввод через IndexedDB
- **Принято:** запись сначала в локальную IndexedDB-очередь, потом async к серверу. `client_generated_id` для идемпотентности.
- **Отвергнуто:** синхронная отправка с ожиданием ответа.
- **Почему:** «5 секунд и забыл» — священный сценарий. Плохой интернет не должен ломать ввод.

## Модель данных

### D1. Без мультивалютности в v1
- **Принято:** только RUB в v1.
- **Отвергнуто:** 5 валют с самого начала.
- **Почему:** автор не планирует валютных трат в ближайший год. Усложнение модели не оправдано. Возвращаем в v2+ через ЦБ РФ API.

### D2. Decimal для денег, не float
- **Принято:** `@db.Decimal(p,s)` через Prisma.
- **Отвергнуто:** float, JS number, PostgreSQL `money` тип.
- **Почему:** финансовые расчёты не терпят накопления ошибок округления.

### D3. Категории до 2 уровней в Common, произвольно в Pro
- **Принято:** в БД произвольная глубина через `parent_id`, в UI v1 — до 2 уровней.
- **Отвергнуто:** жёсткое ограничение глубины в БД.
- **Почему:** для большинства юзеров 2 уровня — оптимум скорости ввода. Глубокая иерархия — Pro-сценарий.

### D4. Цели накопления через виртуальные счета
- **Принято:** цель = счёт типа `savings`. Пополнение = `transfer`. Изъятие = `transfer` обратно.
- **Отвергнуто:** категория «Накопления» в дереве категорий как изначально планировалось.
- **Почему:** Чище семантика. Перевод в накопления — не расход, но уменьшает оперативные средства и дневной бюджет. Изъятие — не доход.

### D5. Три группы счетов: Current, Savings, Debt
- **Принято:** счёт имеет атрибут `group`. Группа Debt — единственная с отрицательными балансами.
- **Отвергнуто:** обычный счёт с типом «кредитный».
- **Почему:** Обобщённая семантика для всех типов займов (кредитки, кредиты наличными, займы у частных лиц).

### D6. Один тап = одна транзакция, без splits
- **Принято:** каждая категория из чека — отдельная транзакция.
- **Отвергнуто:** модель `transaction_split` с родителем и дочерними записями.
- **Почему:** простота ввода важнее «один чек как одна сущность». Если позже окажется нужно — добавим опциональный `merchant` через миграцию.

### D7. Компенсации через `gross_amount` + `net_amount`
- **Принято:** опциональные поля на транзакции (флажок «была компенсация»).
- **Отвергнуто:** отдельная сущность `compensation` с типами (cashback / discount / promo / bonus / refund).
- **Почему:** простая модель покрывает основные кейсы (СберСпасибо, Яндекс Плюс, компенсация обедов работодателем).

### D8. Кэшбэк постфактум — обычный доход
- **Принято:** категория «Кэшбэк/возвраты» в дереве доходов.
- **Отвергнуто:** ретроспективная привязка кэшбэка к исходным покупкам.
- **Почему:** Без банковской интеграции аккуратно связать невозможно.

### D9. Возвраты через статус `cancelled` + linked transaction
- **Принято:** возврат меняет статус исходной транзакции на `cancelled` или создаёт `linked_transaction` для частичных.
- **Отвергнуто:** возврат как новая независимая транзакция.
- **Почему:** Семантически правильно (возврат ≠ доход). UX требует отдельной проработки (см. `OPEN_QUESTIONS.md`).

### D10. JSON-экспорт с `schemaVersion`, без миграторов
- **Принято:** поля `schemaVersion`, `appVersion`, `exportedAt`. При импорте старого — предупреждение.
- **Отвергнуто:** полноценная система миграции v1 → v2 → v3.
- **Почему:** минимальная защита от случайностей при минимальной стоимости разработки.

### D11. Без отдельной модели ledger / journal
- **Принято:** простая модель «транзакция = одна строка».
- **Отвергнуто:** double-entry ledger с journal/lines.
- **Почему:** принцип Парето. Полноценная бухгалтерия превращает приложение в приборную панель самолёта. Цель — контроль cashflow, не учёт долгов.

### D12. Запланированные платежи = статус `pending`
- **Принято:** разовые запланированные платежи используют тот же `pending` статус, что и подписки.
- **Отвергнуто:** отдельный статус `scheduled`.
- **Почему:** упрощение. Не важно, откуда пришёл pending — он всегда обрабатывается одинаково.

### D13. Создание подписок/правил — НЕ на главном экране
- **Принято:** калькулятор главного экрана — только для уже произошедших или вот-вот происходящих движений. Подписки — отдельный раздел.
- **Отвергнуто:** ввод подписок через тот же калькулятор.
- **Почему:** концептуально другая операция. Главный экран должен быть быстрым.

## Процесс

### P1. AGENTS.md + CLAUDE.md (симлинк), разделы по типам
- **Принято:** AGENTS.md — основной файл. CLAUDE.md — симлинк/копия. Структура по разделам типа правил.
- **Отвергнуто:** длинный «свалка требований» файл.
- **Почему:** короткие правила в чётких разделах — Codex/Claude применяют. Длинные тексты игнорируются.

### P2. Claude Design подключается к репо через GitHub Integration
- **Принято:** Claude Design читает компоненты, стили, конфиг проекта напрямую из репозитория. DESIGN.md дополняет принципами.
- **Отвергнуто:** работа Claude Design «в вакууме» с одним DESIGN.md.
- **Почему:** официальная GitHub-интеграция даёт 80% контекста автоматически.

### P3. Уведомления Telegram: 3 типа в v1
- **Принято:** pending к подтверждению, плановые напоминания, операционные алерты (admin only).
- **Отвергнуто:** проверка баланса карты, push при превышении дневного бюджета, дайджесты.
- **Почему:** приложение не ведёт баланс банковских счетов; некритичные алерты идут в in-app inbox.

### P4. Codex как основной инструмент
- **Принято:** Codex для бэкенда, UI-реализации, инфраструктуры. Claude Design для визуала.
- **Отвергнуто:** Claude Code как основной (слишком жёсткие лимиты).
- **Почему:** шире лимиты, multi-agent режим, более стабильная работа.

### P5. Tier-разметка с первого дня, UI без разделения
- **Принято:** каждая фича имеет тег Common/Pro. UI в v1 един (Pro-режим для автора).
- **Отвергнуто:** полноценный двойной UI с переключателем в v1.
- **Почему:** без реальных Common-юзеров нельзя честно спроектировать Common-режим. Это отдельный эпик v2+.
