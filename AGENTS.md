# AGENTS.md

## Что это и как использовать

Этот файл — единственный источник операционных правил для всех AI-агентов проекта (Codex, Claude Code, Cursor, Claude Design). Все правила здесь обязательны к соблюдению при выполнении любой задачи в этом репозитории.

Если правило в этом файле конфликтует с указанием пользователя в текущем промпте — выполни задачу пользователя, но в описании PR явно укажи, какое правило AGENTS.md было нарушено и почему.

Если правило здесь конфликтует с правилом в nested AGENTS.md (например, `src/services/AGENTS.md`) — побеждает ближайший к редактируемому файлу AGENTS.md, как определено спецификацией agents.md.

`CLAUDE.md` в корне репозитория — это технический импорт этого файла для агентов семейства Claude. Правки вносятся только сюда, в `AGENTS.md`.

## Code map

Карта репозитория для быстрой навигации агентом. Раздел заполняется в эпике 2 после создания базового скелета Next.js. До этого момента раздел пуст.

**Формат раздела — древовидный (ASCII-tree), аналогично разделу «Структура репозитория» в README.md, но с большей глубиной.** Показываются директории первого и второго уровня, ключевые точки входа (entry points), расположение Prisma schema, сервисного слоя, тестов, конфигурации. Файлы внутри директорий не перечисляются, кроме явных entry points (например, `app/layout.tsx`, `prisma/schema.prisma`).

**Мандат на обновление code map.** При выполнении любой стори, в которой:
- появляется новая директория первого или второго уровня;
- переименовывается или переезжает ключевая точка входа;
- меняется расположение Prisma schema, сервисного слоя, тестов, конфигурации;
- добавляется новая директория с собственным nested AGENTS.md,

AI-агент обязан обновить раздел «Code map» в том же PR. Изменения внутри одной директории (новые файлы того же типа) в code map не отражаются — карта описывает структуру, а не содержимое.

## Мандат на ведение документации

После завершения любой стори AI-агент обязан выполнить следующие действия в том же PR, в котором делается код.

**1. Обновить PLAN.md:**
- Пометить выполненные задачи (поставить отметку выполнения в таблице задач стори).
- Если стори завершена полностью — отметить это в строке «Текущая стори» блока «Текущая позиция»: перенести её в «Последняя завершённая», а в «Текущая стори» поставить следующую по плану.
- Обновить блок «Ключевые решения последних грумингов» (оставить последние 3–5 пунктов).
- Если в работе появились новые открытые вопросы — добавить их в раздел открытых вопросов в PLAN.md.

**2. Обновить README.md** — только если изменилось одно из:
- Технологический стек (добавлен или убран сервис, поменялась мажорная версия фреймворка).
- Состав или назначение документов в корне репозитория.

Косметические правки README запрещены — это файл с низкой частотой изменений.

**3. Обновить AGENTS.md (этот файл)** — по правилам в следующей секции.

**4. Обновить BACKLOG.md** — только если в груминге явно принято решение о переносе функциональности в v2/v3 или об окончательном отказе. Самовольно добавлять идеи в BACKLOG.md агенту запрещено.

**5. Не обновлять DESIGN.md** без явного запроса пользователя. Этот файл наполняется в эпике 2 совместно с Claude Design.

## Мандат на обновление этого файла

AI-агент добавляет новое правило в AGENTS.md, если выполнено одно из условий:

- В процессе грумминга или работы принято архитектурное решение, которое будет применимо более чем в одной стори (например: «все money-поля используют тип Decimal»).
- AI-агент или пользователь обнаружил антипаттерн, который агент совершил и должен впредь не совершать (например: «не использовать `SELECT *` в Prisma-запросах к таблице transactions»).
- Появилось известное ограничение библиотеки или инструмента, на которое агент натолкнулся (например: «Next.js 15: `cookies()` асинхронный, использовать `await cookies()`»).

Правило добавляется в соответствующий раздел: «Архитектурные инварианты», «Запреты», «Известные ограничения инструментов» или «Don't-touch зоны».

**Формат правила.** Одна строка списка. Однозначное действие в повелительном наклонении или явный запрет. Без оправданий и без «почему». Хорошо: «Денежные суммы хранятся как Decimal, не как number/float.» Плохо: «Старайся использовать Decimal для денег, потому что float теряет точность».

Если правило требует объяснения — оно добавляется второй строкой в скобках после правила, максимум одно предложение. Пример: «Денежные суммы хранятся как Decimal, не как number/float. (Float теряет точность на сложении транзакций; ошибка проявляется через месяц-два эксплуатации, тяжело отловить.)».

**AI-агент не имеет права удалять правила из AGENTS.md.** Если в процессе работы AI-агент обнаружил, что какое-то правило стало неактуальным (например, отменено более новым архитектурным решением, или относится к удалённому модулю), AI-агент обязан написать об этом в описании PR отдельным пунктом «Кандидаты на удаление из AGENTS.md» с указанием правила и причины. Решение об удалении принимает пользователь вручную.

**Обязательный блок в описании каждого PR.** В тело PR AI-агент добавляет два пункта:
- «Новые правила в AGENTS.md: …» — список добавленных правил или «нет».
- «Кандидаты на удаление из AGENTS.md: …» — список устаревших правил с обоснованием или «нет».

Эти пункты обязательны даже если в обоих случаях «нет» — это явное подтверждение, что AI-агент проверил необходимость обновления.

**Nested AGENTS.md.** Если правило применимо только к одному модулю (например, только к сервисному слою, только к Telegram-боту, только к Prisma-миграциям) — оно создаётся в AGENTS.md внутри соответствующей директории, а не в корневом AGENTS.md. Корневой AGENTS.md содержит только правила, применимые ко всему проекту. Это профилактика разрастания корневого файла.

## Архитектурные инварианты

Раздел заполняется по мере появления решений в процессе работы. Ниже — инварианты, зафиксированные до старта разработки и применимые с первой стори.

- Денежные суммы хранятся и передаются как `Decimal` (тип Prisma `Decimal` для БД, библиотека `decimal.js` для логики приложения). Не использовать JavaScript `number` или `float` для любых денежных полей, включая промежуточные расчёты. (Float теряет точность на сложении транзакций; ошибка проявляется через месяц-два эксплуатации, тяжело отловить.)
- Миграции Prisma только аддитивные в v1: добавление новых полей, таблиц, индексов. Запрещено удаление колонок, переименование колонок, изменение типа существующих колонок. (Откат деструктивной миграции на проде требует ручного восстановления; в v1 безопаснее накопить «мёртвые» колонки и почистить их одной миграцией перед v2.)

## Запреты

Раздел заполняется по мере появления решений. Ниже — запреты, зафиксированные до старта разработки и применимые с первой стори.

- Запрещено использовать `pages/api/`. API-эндпоинты создаются только через Route Handlers в `app/api/`. (Next.js 15 App Router; смешивание двух подходов создаёт два источника правды по маршрутизации и аутентификации.)
- Запрещено добавлять Redis, BullMQ или любой другой брокер сообщений и кэш-сервис в v1. Фоновые задачи выполняются Postgres-воркером на основе таблицы заданий с `SKIP LOCKED`. (Решение зафиксировано в BACKLOG.md как категорический отказ для v1; пересмотр возможен только при доказанной проблеме производительности.)

## Стиль кода и Git

**Импорты.** Порядок блоков: external → internal (`@/...`) → relative (`./...`). Между блоками одна пустая строка. Внутри блока — алфавитный порядок по имени модуля.

**Имена файлов:**
- Компоненты React: PascalCase (`ExpenseCard.tsx`).
- Хуки: camelCase с префиксом `use` (`useTransactions.ts`).
- Утилиты, сервисы, типы: camelCase (`formatCurrency.ts`, `transactionService.ts`).
- Тесты: рядом с тестируемым файлом, суффикс `.test.ts` или `.test.tsx`.

**Ветки:**

**Стратегия веток.** Все рабочие ветки (`feature/*`, `fix/*`, `chore/*`) создаются от `main` и мержатся обратно в `main` через PR. Прямой push в `main` запрещён.

**Деплой.** Мерж в `main` автоматически деплоится на stage. Деплой в prod — создание git-тега формата `vX.Y.Z` (SemVer) на коммите в `main` через GitHub Releases. Тег создаёт пользователь вручную. Агенты теги не создают и не удаляют. Откат prod-релиза — повторный деплой предыдущего тега.

- `feature/<short-kebab-name>` — новая функциональность.
- `fix/<short-kebab-name>` — багфикс.
- `chore/<short-kebab-name>` — инфраструктура, зависимости, документация.

**Коммиты — Conventional Commits с русским сообщением в повелительном наклонении.**

Префиксы:
- `feat:` — новая функциональность.
- `fix:` — багфикс (только если соответствует определению бага из раздела «Что такое баг»).
- `refactor:` — изменение кода без изменения поведения.
- `chore:` — инфраструктура, зависимости, документация.
- `docs:` — изменения только в .md-файлах.

Сообщение: повелительное наклонение, русский язык. Хорошо: `feat: добавить экспорт транзакций в JSON`. Плохо: `feat: added export` или `feat: добавил экспорт`. Тело коммита (если есть) объясняет «почему», а не «что» — «что» видно по diff.

**Язык комментариев в коде:** русский. Технические термины (Route Handler, Decimal, Service Layer, IndexedDB) пишутся на английском без перевода.

## Pull requests

**Описание PR содержит (в этом порядке):**
1. Какая стори (или какие стори) из PLAN.md закрывается этим PR. Указывать названиями стори текстом, не идентификаторами.
2. Что сделано — список из 3–7 пунктов.
3. Как протестировано — какие автотесты прогонялись, какие сценарии проверялись руками если применимо.
4. Новые правила в AGENTS.md: список или «нет».
5. Кандидаты на удаление из AGENTS.md: список с обоснованием или «нет».
6. Открытые вопросы, возникшие в работе: список или «нет».

**Язык описания PR — русский.** Заголовок, тело, все пункты чек-листа пишутся на русском. Технические термины (Route Handler, Decimal, CI, PR) пишутся на английском без перевода — аналогично правилу для комментариев в коде.

**Шаблон PR обязателен.** При создании/открытии PR AI-агент использует структуру из файла .github/pull_request_template.md. Все разделы шаблона заполняются — пустых разделов быть не должно.

**Размер PR — ориентир, не правило.** Целевой размер до 400 строк изменений (без учёта lock-файлов, миграций, автогенерируемого кода). Если PR превышает 600 строк — это сигнал обсудить с пользователем перед коммитом, не была ли стори слишком крупной. Решение об объединении нескольких мелких стори в один PR или о разбиении одной стори на несколько PR принимается пользователем на этапе грумминга, не агентом.

**Перед открытием PR.** AI-агент выполняет все обязательные проверки локально (`type-check`, `lint`, тесты). Если что-то падает — фиксит, не открывает PR с красными чеками. Точный список команд закрепится в эпике 1 после настройки инструментария.

## Don't-touch зоны

AI-агент не имеет права изменять следующее без явного запроса пользователя:

- Файлы `.env`, `.env.local`, `.env.production` и любые другие файлы окружения с секретами. AI-агент может создать `.env.example` с именами переменных без значений.
- Содержимое директории `prisma/migrations/` — существующие миграции неизменяемы. Новые миграции добавляются только через команду `prisma migrate dev`, имена файлов и их порядок не редактируются вручную.
- Содержимое директории `.github/workflows/` — изменения CI-пайплайна согласовываются отдельной стори, не как побочный эффект фичи.
- Конфигурация Caddy и Docker Compose для prod-окружения (когда появятся файлы).
- Любые файлы и переменные с упоминанием prod-домена, prod-токенов, prod-БД. В коде и тестах допустимы только stage-домен, stage-токены, stage-БД.

(Раздел уточнится в эпике 1 с появлением конкретных файлов конфигурации.)

## Runbook'и: когда создавать и как

**Runbook** — это пошаговая инструкция для редкой операционной процедуры, при которой ошибка дорого стоит. Не для разработки, а для эксплуатации проекта.

**Когда AI-агент обязан создать runbook.** Если стори содержит хотя бы одну из следующих процедур, в той же стори обязательна задача создания runbook'а в `docs/runbooks/<имя>.md`:

- Резервное копирование данных (создание, проверка, ротация).
- Восстановление данных из любого источника (Backblaze B2, JSON-экспорт, ручной дамп).
- Деплой на stage или prod, откат деплоя.
- Перевыпуск credentials (Google OAuth, Telegram bot token, Backblaze B2 keys) при компрометации или плановой ротации.
- Добавление нового пользователя в whitelist (Telegram-бот, OAuth-приложение).
- Ручной запуск или остановка фонового воркера.
- Применение или откат миграции БД в prod-окружении.
- Подъём stage или prod с нуля на новом VPS.

**Структура файла runbook'а:**
1. Цель — одно предложение: что эта процедура делает.
2. Когда применяется — триггер: «после компрометации credentials», «раз в полгода», «при сообщении такого-то от мониторинга».
3. Предусловия — что должно быть настроено и доступно (SSH-ключ к VPS, доступ к Backblaze B2 console, и т.д.).
4. Шаги — нумерованный список с точными командами и ожидаемым выводом каждой команды.
5. Что делать при ошибке — минимум для шагов, где ошибка приводит к потере данных.
6. Проверка успешности — как убедиться, что процедура завершилась корректно.

**Каждый шаг runbook'а должен быть проверен в текущей итерации.** Если AI-агент пишет шаг, который не был выполнен фактически в работе над стори (просто «по логике должно работать»), он обязан явно пометить шаг тегом `[НЕ ПРОВЕРЕНО]` и упомянуть это в описании PR. Пользователь решает, нужно ли проверить шаг руками до мержа.

**Стори с операционной процедурой без runbook'а не считается завершённой.** В PLAN.md задача не помечается как выполненная, PR не мержится.

## Что такое баг

Определение бага в этом проекте намеренно жёсткое, чтобы файл `docs/bugs.md` (когда он появится) не превратился в свалку всех неудач.

**Баг — это ситуация, при которой работающий код перестал работать или работал неправильно с момента написания, и причина была устранена изменением кода или конфигурации.**

**Не баг:**
- Изначально неверная логика, обнаруженная до релиза стори в основную ветку. Это часть итерации разработки.
- Уточнение или изменение требований в груминге. Это новое требование, оформляется как новая задача в стори.
- AI-агент сделал не то, что просили в промпте. Это коррекция в AGENTS.md (добавляется правило, чтобы не повторилось), не баг.
- Изменение мнения пользователя о том, как фича должна работать. Это новое требование.
- Сетевая ошибка, временный сбой внешнего сервиса. Это инфраструктурная проблема, в `docs/bugs.md` не пишется.

`docs/bugs.md` создаётся по факту первого настоящего бага, не превентивно. Когда файл создаётся, его шаблон записи: дата, краткое описание симптома, причина, исправление (ссылка на коммит), правило-профилактика в AGENTS.md (если применимо).

## Известные ограничения инструментов

Раздел пополняется по мере столкновения с конкретными ограничениями библиотек, фреймворков, версий рантайма. Каждая запись — одна строка с действием.

Раздел изначально пуст. AI-агент добавляет сюда правила, когда натыкается на ограничение в работе. Пример формата (появится позже):
- Next.js 15: `cookies()`, `headers()`, `params` — асинхронные. Использовать `await cookies()`, не синхронный вызов.
